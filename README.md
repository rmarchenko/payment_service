# Асинхронный сервис процессинга платежей

Микросервис для асинхронного приема и обработки платежей с гарантированной доставкой сообщений через паттерн Transactional Outbox.

### Архитектурные особенности:
* **Transactional Outbox Pattern**: Атомарная запись платежа и события в БД в рамках одной ACID-транзакции. Исключает потерю сообщений при недоступности брокера.
* **Строгая идемпотентность**: Использование заголовка `Idempotency-Key` защищает систему от дублирования списаний при повторных сетевых запросах.
* **Экспоненциальный Retry**: Автоматический перезапуск отправки Webhook-уведомлений клиенту при сетевых сбоях (3 попытки с увеличивающейся паузой).
* **Dead Letter Queue (DLQ)**: Автоматическая изоляция необработанных сообщений в очередь брокера `payments.dlq` для последующего анализа.

---

## 🛠 Стек технологий

* **Backend**: FastAPI (Python 3.11) + Pydantic v2
* **Database**: PostgreSQL 15 + SQLAlchemy 2.0 (Async mode)
* **Message Broker**: RabbitMQ + FastStream
* **Migrations**: Alembic

---

## 🚀 Быстрый запуск (Docker Compose)

Проект оптимизирован под современные версии **Docker Engine** и **Docker Desktop** (с поддержкой спецификации `Compose V2`).

Для сборки и запуска всей инфраструктуры одной командой выполните:

```bash
docker compose up --build
```

**Состав разворачиваемого окружения:**
1. `db`: База данных PostgreSQL (порт `5432`).
2. `rabbitmq`: Брокер сообщений с Web Management UI (порт `5672`, веб-панель: http://localhost:15672, логин/пароль: `guest`/`guest`).
3. `api`: Веб-приложение FastAPI (порт `8000`). Автоматически применяет миграции Alembic при старте. Также содержит встроенный mock-приемник вебхуков для сквозного тестирования.
4. `outbox-worker`: Фоновый демон, переносящий транзакции из таблицы Outbox в RabbitMQ.
5. `consumer`: Асинхронный обработчик FastStream, выполняющий эмуляцию платежного шлюза.

## 📡 Примеры использования API

Интерактивная документация Swagger доступна по адресу: http://localhost:8000/docs

### 1. Создание платежа (POST `/api/v1/payments`)
Реализован асинхронный ответ `202 Accepted`. Требует передачи обязательного уникального заголовка `Idempotency-Key`.

**Запрос (cURL):**
```bash
curl -X 'POST' \
  'http://localhost:8000/api/v1/payments' \
  -H 'X-API-Key: super-secret-static-key' \
  -H 'Idempotency-Key: payment-uuid-v4-example-1001' \
  -H 'Content-Type: application/json' \
  -d '{
  "amount": 2500.00,
  "currency": "RUB",
  "description": "Оплата подписки",
  "metadata": {
    "user_id": 42
  },
  "webhook_url": "http://api:8000/test-client/webhook"
}'
```

**Ответ (202 Accepted):**
```json
{
  "id": "e3b0c442-98fc-4bcb-8912-32117a5cc2a4",
  "status": "pending",
  "created_at": "2026-08-07T16:20:00.123456"
}
```

> **Проверка идемпотентности**: Повторите точно такой же запрос с тем же `Idempotency-Key`. Вы мгновенно получите тот же самый ответ без повторного создания записи в БД или повторной отправки события в очередь.

---

### 2. Получение информации о платеже (GET `/api/v1/payments/{payment_id}`)
Позволяет узнать актуальное состояние транзакции в базе данных. В качестве `payment_id` укажите `id` из предыдущего ответа.

**Запрос (cURL):**
```bash
curl -X 'GET' \
  'http://localhost:8000/api/v1/payments/e3b0c442-98fc-4bcb-8912-32117a5cc2a4' \
  -H 'X-API-Key: super-secret-static-key'
```

**Ответ (200 OK):**
```json
{
  "id": "e3b0c442-98fc-4bcb-8912-32117a5cc2a4",
  "amount": 2500.00,
  "currency": "RUB",
  "description": "Оплата подписки",
  "metadata_json": {
    "user_id": 42
  },
  "status": "succeeded",
  "idempotency_key": "payment-uuid-v4-example-1001",
  "webhook_url": "http://api:8000/test-client/webhook",
  "created_at": "2026-08-07T16:20:00.123456",
  "processed_at": "2026-08-07T16:20:03.456789"
}
```

## 🛠 Проверка сценариев отказоустойчивости (DLQ)

Для проверки ухода сообщений в Dead Letter Queue (очередь для необработанных сообщений):
1. Отправьте платеж через cURL, указав заведомо несуществующий домен в параметре `webhook_url` (например, `http://invalid-client-domain.xyz`).
2. В логах контейнера `consumer` отобразятся **3 попытки отправки** вебхука с экспоненциальной задержкой (1с -> 2с -> 4с).
3. После третьей неудачи FastStream автоматически переместит сообщение из основной очереди `payments.new` в изолированную очередь брокера **`payments.dlq`**.
4. Состояние очереди можно проверить визуально в панели управления RabbitMQ Management UI в разделе **Queues**.
